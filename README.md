# Codzee Task Manager

A local Django REST Framework task API for evaluating Codzee's pull request reviews.
This baseline uses SQLite and provides task CRUD at `/api/tasks/`.

## Local setup (macOS)

Use Python 3.11 (the original environment uses Python 3.11.6). Run these commands
from the repository root. If `venv` already exists, skip its creation.

```sh
git clone https://github.com/subhashree1993/codzee-task-manager.git
cd codzee-task-manager
python3.11 -m venv venv
venv/bin/python -m pip install -r requirements.txt
export DJANGO_SECRET_KEY="$(venv/bin/python -c 'from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())')"
venv/bin/python manage.py migrate
venv/bin/python manage.py runserver
```

Open <http://127.0.0.1:8000/api/tasks/> in a browser or use the examples below.
Keep the server running and use a second terminal for curl commands.
The SQLite database is `db.sqlite3` in the repository root; migrations create it.

Settings read `DJANGO_SECRET_KEY` from the environment. If it is unset or empty,
they use a clearly marked, insecure **local development only** fallback.
`.env` files are ignored by Git but are not loaded automatically; export the
variable in your shell. These settings use `DEBUG=True` and are for local use.
Virtual environments, SQLite databases, Python caches, and `.env` files are
excluded from commits.

## Task API

| Field | Behaviour |
| --- | --- |
| `id` | Generated by the server; read only. |
| `title` | Required text, maximum 200 characters. DRF trims surrounding whitespace and rejects blank titles. |
| `description` | Optional text; defaults to an empty string. |
| `status` | One of `pending`, `in_progress`, or `completed`; defaults to `pending`. |
| `created_at` | Timestamp generated on creation; read only. |
| `owner` | Authenticated task owner; assigned by the server and read only. |

The status migration preserves `pending`, `in_progress`, and `completed`, maps
legacy `done` values to `completed`, and maps other unknown values to `pending`.

All task endpoints require HTTP Basic Authentication. Each user can access only
their own tasks. Task lists support status filtering, case-insensitive search,
and page-number pagination, ordered by newest creation time and then descending
ID.

### List filters and pagination

Only `GET /api/tasks/` uses list query parameters:

| Parameter | Behaviour |
| --- | --- |
| `status` | Optional exact status filter: `pending`, `in_progress`, or `completed`. Missing or empty means no status filter. Unknown nonempty values return 400 with a `status` error. |
| `search` | Optional Unicode-aware, case-insensitive literal substring search across title and description. Surrounding whitespace is trimmed; missing or whitespace-only values disable search. |
| `page` | One-based page number; defaults to 1. |
| `page_size` | Results per page; defaults to 10 and is capped at 100. |

Status and search filters combine with AND. Filtering happens before pagination,
and all results and counts are scoped to the authenticated user.

The list response is now an object rather than a bare array:

```json
{
  "count": 1,
  "next": null,
  "previous": null,
  "results": [
    {
      "id": 1,
      "title": "Prepare interview",
      "description": "Review the assignment",
      "status": "pending",
      "created_at": "2026-10-12T12:00:00Z",
      "owner": 1
    }
  ]
}
```

An invalid page or page beyond the available range returns 404, following DRF's
`PageNumberPagination` behavior. A nonnumeric or non-positive `page_size` falls
back to the default; a value above 100 is capped at 100.

### Local authentication

Create a local account and enter a username and password when prompted:

```sh
venv/bin/python manage.py createsuperuser
```

Use the username-only form `curl -u your-username`; curl will prompt for the
password. Unauthenticated requests return
`401 Unauthorized`. Basic Authentication credentials are only encoded, not
encrypted; use HTTPS outside local development.

The ownership migration assigns pre-existing tasks to an inactive account named
`legacy-task-owner` (with a numeric suffix if that username is already taken).
An upgrade migration repairs the reserved email marker for an account left with
a blank email by the original migration. It acts only when exactly one account
has the exact generated username form (`legacy-task-owner` or a numeric suffix),
is inactive, has an unusable password, has a blank email, and owns tasks. It
preserves active accounts, usable passwords, and nonblank emails. If the marker
already exists or multiple accounts qualify, the migration makes no change.

Before any manual repair or reassignment, inspect unmarked candidates and their
owned task IDs in `manage.py shell`:

```python
import re

from django.contrib.auth import get_user_model
from tasks.models import Task

User = get_user_model()
legacy_username = re.compile(r"legacy-task-owner(?:-[0-9]+)?")
for candidate in User.objects.filter(is_active=False, password__startswith="!"):
    if legacy_username.fullmatch(candidate.username) is None:
        continue
    if (candidate.email or "").strip():
        continue
    print({
        "id": candidate.pk,
        "username": candidate.username,
        "email": candidate.email,
        "active": candidate.is_active,
        "has_usable_password": candidate.has_usable_password(),
        "task_ids": list(
            Task.objects.filter(owner_id=candidate.pk).values_list("id", flat=True)
        ),
    })
```

If more than one unmarked account appears, do not choose based on the username
alone. Verify the exact account and its task IDs against the pre-migration
database or other authoritative records. If you cannot verify a single account,
stop and leave the accounts and tasks unchanged. After verifying the exact ID,
first confirm no other account already has the reserved marker. If a marker
already exists, verify that account and its task IDs instead of marking another.
You may set the marker explicitly only after those checks:

```python
legacy_owner = User.objects.get(pk=VERIFIED_LEGACY_OWNER_ID)
assert re.fullmatch(r"legacy-task-owner(?:-[0-9]+)?", legacy_owner.username)
assert not legacy_owner.is_active
assert not legacy_owner.has_usable_password()
assert not (legacy_owner.email or "").strip()
assert not User.objects.filter(email="legacy-task-owner@codzee.invalid").exists()
assert Task.objects.filter(owner_id=legacy_owner.pk).exists()
legacy_owner.email = "legacy-task-owner@codzee.invalid"
legacy_owner.save(update_fields=["email"])
```

Once the exact account is marked, reassignment uses its numeric owner ID, never
a username prefix. Replace `LEGACY_OWNER_ID` with the verified integer and the
destination username with an active account:

```python
legacy_owner = User.objects.get(pk=LEGACY_OWNER_ID)
assert not legacy_owner.is_active
assert not legacy_owner.has_usable_password()
destination = User.objects.get(username="your-active-username")
Task.objects.filter(owner_id=legacy_owner.pk).update(owner_id=destination.pk)
```

| Method | URL | Successful result |
| --- | --- | --- |
| GET | `/api/tasks/` | 200: list of tasks |
| POST | `/api/tasks/` | 201: created task |
| GET | `/api/tasks/<id>/` | 200: one task |
| PUT | `/api/tasks/<id>/` | 200: updated task; title is required |
| PATCH | `/api/tasks/<id>/` | 200: updated task; omitted fields remain unchanged |
| DELETE | `/api/tasks/<id>/` | 204: empty response |

Invalid request fields return 400 with field errors. A missing task returns 404.
The URLs include trailing slashes.

### Examples

Pass `-u your-username` on each curl command below; curl prompts for the password.

Create a task:

```sh
curl -i -u your-username -X POST http://127.0.0.1:8000/api/tasks/ \
  -H 'Content-Type: application/json' \
  -d '{"title":"Prepare interview","description":"Review the assignment","status":"pending"}'
```

The response includes the assigned `id` and `created_at`. Replace `1` in the
following commands with the actual returned ID.

```sh
# List and retrieve
curl -u your-username http://127.0.0.1:8000/api/tasks/
curl -u your-username http://127.0.0.1:8000/api/tasks/1/

# Filter and search the authenticated user's tasks
curl -u your-username 'http://127.0.0.1:8000/api/tasks/?status=pending&search=interview&page=1&page_size=10'

# Update the task's editable fields
curl -i -u your-username -X PUT http://127.0.0.1:8000/api/tasks/1/ \
  -H 'Content-Type: application/json' \
  -d '{"title":"Prepare interview","description":"Run the tests","status":"in_progress"}'

# Update only the status
curl -i -u your-username -X PATCH http://127.0.0.1:8000/api/tasks/1/ \
  -H 'Content-Type: application/json' \
  -d '{"status":"completed"}'

# Delete
curl -i -u your-username -X DELETE http://127.0.0.1:8000/api/tasks/1/
```

## Checks and tests

```sh
venv/bin/python manage.py check
venv/bin/python manage.py makemigrations --check --dry-run
venv/bin/python manage.py test --verbosity 2
```

The API tests exercise creation, defaults, listing and stable ordering, retrieval,
PUT, PATCH, deletion, authentication, ownership, and server-managed fields.
Django uses a separate test database; these tests do not modify your local tasks.
The migration check verifies that committed migrations match the models.

## Codzee evaluation workflow

Keep this GitHub repository public. Commit and push the working baseline to
`main`, then install and configure Codzee for this repository before opening
evaluation PRs.

1. Task validation: status choices and title validation tests.
2. Authentication and ownership: private tasks, migration handling, permission tests.
3. Filtering and pagination: status/title queries and bounded pagination with tests.

Use a separate branch for each PR. Wait for Codzee's actual review, verify its
comments against the code and tests, and fix confirmed issues on that branch.
Review and merge manually before starting the next PR.
Create `CODZEE_FEEDBACK.md` from actual observations, linking to the PRs and
relevant review comments. Record false positives and missed issues only when
supported by evidence. Submit the assignment form manually after the evaluation.
